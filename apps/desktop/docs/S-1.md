# Spike S-1: PortAudio continuity evidence

**The question** (design §6.2, §11): can a PortAudio capture worker give continuity
evidence equivalent to D-015's on macOS (Core Audio) and on Linux (ALSA `hw:`)? Until it
does on a platform, the Swift app stays the macOS prompted-capture path (D-025), and
nothing about D-015 is relaxed.

The app's capture worker (`voice_lab_desktop/capture/`, D-039) and the harness that
answers the question on real hardware (`scripts/s1-portaudio`, D-040) are built and tested
on the simulated UMIK-1. **Running the harness on the UMIK-1 is the owner's.**

## What the worker checks

One take per worker process, as D-015's Audio Queue worker does. The UMIK-1 only:
anything else is refused before a file exists. PortAudio delivers mono 48 kHz packed
24-bit blocks of a fixed size (default 1,024 frames); the callback copies each block into
a bounded queue and does no IO. A writer thread writes the canonical WAV and reports
`<bytes>\n` per block written, which is the take's clock (D-014).

For every block, `capture/timing.py` checks:

| Check | Fails the take when |
| --- | --- |
| An ADC time | `time.inputBufferAdcTime` is 0, negative or not finite (PortAudio has none) |
| Continuity | `adc(i) - (adc(i-1) + frames(i-1) / 48000)` is more than the tolerance (default ±64 frames, 1.3 ms) |
| No loss upstream | PortAudio flags `input_overflow` or `input_underflow` |
| No loss downstream | the writer's queue is full (the take stops; nothing is dropped) |
| Accounting | the frames written differ from the frames accepted |

The first failure stops the take and keeps what was written. Samples are never inserted
to cover a gap. The evidence (`continuity.json`, `voice-lab-desktop.portaudio-continuity/v1`)
is written on success and on failure: private, at most 16 KiB, and bound to the WAV's
SHA-256, size, frame count and name. The parent (`capture/process.py`) validates it and
inspects the WAV before the take exists as `original.wav`. Missing, malformed,
unsuccessful or mismatched evidence fails closed. The evidence stays on the capturing
machine; a capture package never carries it.

### Why an ADC time, and what PortAudio cannot give

PortAudio exposes no device sample counter. D-015 checks Audio Queue's `mSampleTime` to
1e-6 frames. The nearest PortAudio fact is each block's ADC time on the stream clock:

- Core Audio derives it from the buffer's host time.
- ALSA derives it from the status timestamp and the capture delay.

These times carry jitter, so the rule needs a tolerance. The tolerance absorbs jitter,
not loss: a lost host buffer moves the ADC time by a whole buffer (hundreds of frames),
and jitter does not accumulate because each block is compared with the block before it.
The largest deviation seen in each take is in its evidence, so the tolerance can be judged
from data. That is the spike.

| D-015 has | The PortAudio worker has | Gap |
| --- | --- | --- |
| Device sample time, valid flag, exact to 1e-6 frames | ADC time × 48 kHz, ± a tolerance | Jitter needs a tolerance; no validity flag (0 means none) |
| Audio Queue overload/converter status | `input_overflow`/`input_underflow`, reported after the fact | No count of lost frames; whether Core Audio flags input-only overflows is for the run to show |
| The selected Core Audio device UID | PortAudio's device name and host API; on Linux, `hw:card,dev` and `/proc/asound/cardN/usbid` | No UID on macOS |
| Mid-stream format/converter errors | `fail_if_conversion_required` on macOS; `hw:` cannot convert; a stream that stops by itself fails | No format-change event |

## What the harness does

```sh
scripts/s1-portaudio --output DIR [--takes 20 --seconds 3] [--cold-takes 20 --cold-seconds 1 \
    --cold-idle-seconds 5] [--long-takes 2 --long-seconds 60] [--max-duration-seconds 2] \
    [--block-frames 1024] [--tolerance-frames 64] [--simulated JSON]
```

It records takes with the same worker the Record: prompts screen uses:

| Variant | Takes |
| --- | --- |
| Cold starts | Each after an idle pause and a fresh device listing |
| Warm takes | Back to back |
| Long takes | Two 60-second takes |
| Maximum duration | One take the worker stops by itself |

Every take except the last is stopped by request.

Each take is checked again from disk on its own, independently of the worker and of the
parent's first check (`takes/NNN-*/python-validation.json`). The harness then writes:

| Path | What it holds |
| --- | --- |
| `benchmark/report.json` | Latencies (record to first confirmed frames, cold start, stop to the worker, stop to a validated take), the timer/frame agreement and the worker's memory growth. The verdicts are computed by the existing benchmark's own rules and thresholds (`tests/recording_latency_benchmark.py`); rows it cannot measure stay `not-measured`. |
| `verification/verification.json` | The variants exercised, waveform extrema from the written files, and the S-1 results |
| `matrix/` | `scripts/recording_acceptance_matrix.py` run over the two |
| `s1-report.md` and `s1-report.json` | The verdict |

**The verdict.** `passed` needs all of the following. Otherwise the verdict is `failed`, and the problems are listed.

- A run on real hardware with the UMIK-1.
- Every take's evidence successful at the declared tolerance.
- No overflow or underflow, and an ADC time for every block.
- Every take re-validated.

A `--simulated` run checks the harness itself and always says `simulated: harness check
only`. The matrix's other rows are not the harness's to answer:

- The parity rows describe the Swift app's interface and processes. The owner judges the
  Record: prompts screen against them.
- The physical-gate rows always need the hardware and a person.

## Running it (owner)

You need a voice-lab checkout whose `.venv` has the development extra (it carries
`sounddevice`), the UMIK-1, and a quiet room. The takes are recordings: the output
directory must be outside the checkout and private. It never enters Git; delete it once
the verdict is recorded.

**macOS (the Air, Core Audio).** Run it from Terminal, which needs microphone access
(System Settings → Privacy & Security → Microphone). Set the UMIK-1 to 48,000 Hz in Audio
MIDI Setup. Use a separate clone, so that the Swift app's environment (the live macOS
path) is not touched:

```sh
git clone https://github.com/scshafe/voice-lab ~/src/voice-lab-s1   # once
cd ~/src/voice-lab-s1 && git pull --ff-only
/opt/homebrew/bin/python3.12 -m venv .venv && .venv/bin/pip install -e '.[dev]'   # once
OUT=~/s1-macos-$(date -u +%Y%m%dT%H%M%SZ) && mkdir -m 700 "$OUT"
scripts/s1-portaudio --output "$OUT"
open "$OUT/s1-report.md"
```

**Linux (ALSA `hw:`).** Use a checkout whose `.venv` has the development extra (README
"Linux"). Install PortAudio with `sudo pacman -S portaudio`. The worker prefers the
UMIK-1's `hw:` device. If PipeWire holds it (`Device unavailable`), stop
PipeWire for the run, then start it again:

```sh
cd ~/src/voice-lab && git pull --ff-only
systemctl --user stop pipewire.socket pipewire pipewire-pulse wireplumber   # only if hw: is busy
OUT=~/s1-linux-$(date -u +%Y%m%dT%H%M%SZ) && mkdir -m 700 "$OUT"
scripts/s1-portaudio --output "$OUT"
systemctl --user start pipewire.socket pipewire pipewire-pulse wireplumber
less "$OUT/s1-report.md"
```

A run with the defaults takes about five minutes. To check the harness first without the
microphone:

```sh
scripts/s1-portaudio --output "$(mktemp -d)" --simulated '{}' --takes 3 --cold-takes 1 --long-takes 0
```

## Reading the report

- **Verdict.** `passed` or `failed`, for this platform.
- **Largest ADC deviation between blocks.** If it is close to the tolerance on a clean
  run, the jitter is too large for the rule. Raise the tolerance only with the data in
  hand, and record why.
- **Problems.** These name the take and the block. A gap shows as `discontinuity`. A lost
  buffer upstream shows as `input overflow`. A host API that has no timestamps shows as
  `no ADC time`.
- **Performance rows.** The latencies and memory against the native app's targets. A row
  with fewer than 20 samples is `underpowered`.

**S-1 passes on a platform** when the verdict there is `passed`. Record the result in
`DECISIONS.md`: the platform, the date, the report's `continuity` block and the commit.
Copy no audio. Until both macOS and Linux pass, the Swift app remains the macOS
prompted-capture path. Prompted uploads from the app stay off on each machine until
then, as the Record: prompts screen's decision says.
