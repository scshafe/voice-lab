# Plan: corpus-first app pipeline — fine-tune directly from the latest recordings

**Goal:** The native app's only workflow beyond recording is **Fine-tune model**: it trains F5-TTS on the latest kept take of every spoken prompt, straight from the library, and shows progress in the app. Groups, sessions, packages, room-tone bindings and "Prepare for lab" disappear from the interface, and the two room-tone prompts leave the catalog (`pilot-v3`, 34 prompts).
**Out of scope:** The in-app Speak (text-to-speech) page — separate plan `2026-09-15-in-app-speak-page.md`, which builds on this one. Deleting the group/reservation data model underneath the recorder (it stays as invisible plumbing; `reserve` still carries a context ID). Retiring the old Qt desktop and the capture console (Step 17 of `2026-09-11-native-recording-ux.md`). The `voice-lab` package/intake/dataset/transfer commands (they stay for the lab's transfer path and are simply not reachable from the app). Hosted training. The 1,000-take acceptance track and physical-test roots (untouched). Consent gating inside the app: nothing leaves the machine; the lab's consent and transfer rules apply unchanged at transfer time.

## Context

- Cole's model (memory `corpus-model-latest-per-prompt`, D-016): corpus = latest kept take per spoken prompt; small continuous revisions; re-tune after each; same Mac records and trains. Decided 2026-09-15: drop the room tones; Fine-tune is an explicit button, never automatic after Save (a two-hour GPU job per take).
- The engine exists as a lab command (`src/cole_voice_lab/finetune.py`, `docs/FINETUNE.md`, plan `2026-09-15-finetune-from-recording-library.md`, committed): `select_finetune_corpus`, `materialize_finetune_dataset`, `describe_finetune_runtime`, `run_f5_finetune`, `synthesize_finetune_samples`, provisioning. This plan wires it into the app's service and UI; it adds no second implementation.
- App seams (checked 2026-09-15): the only visible group/package surface is the footer button `Prepare for lab…` (`apps/macos/Sources/RecordingUI/RecordingTransportControls.swift:42`), the sheet mounted at `RecordingWorkspace.swift:27`, and the flow in `RecordingPackagePreparation.swift` + `RecordingPreparePackageView.swift`. "New setup" fires only automatically on audio reconnect (`RecordingWorkspaceModel.swift:314`). `state.groupID` is plumbing for `reserve` (`RecordingWorkspaceModel.swift:327,351`) and stays.
- Service pattern to mirror: `PreparePackageCommand` → `package_queue.submit` (`recording_service.py:340`, `:531`) → durable queue + one worker process (`recording_package_jobs.py`: `RecordingPackageQueue`, `RecordingPackageSupervisor`) → events `package-preparation` and `package`. Swift side: `RecordingServiceClient.preparePackage` (`RecordingCore/RecordingServiceClient.swift:113`), `applyPackageEvent`.
- Catalog switch precedent: `docs/PROMPT_CATALOG_V2.md` §7 (coverage report before and after, `--expect-catalog-sha256` at build). Spoken prompt hashes are identical across pilot-v1/v2/v3, so every existing take keeps counting; only the room-tone rows vanish.
- Settings: `NativeRecordingApplicationSettings` (`native_recording_application.py:50`) gains `finetune_runtime_root`. Builds are frozen: settings → `scripts/build-native-recording-app` → release verification → copytree install → launch by exact path (handoff: never "Quit & Reopen"; the agent cannot click native UI; ask before presence steps). The app currently running is PID 35990.
- Verification: `scripts/verify-native-recording --suite {contracts,workspace,transport,review,accessibility,package-preparation,recovery,all}` (`scripts/verify_native_recording.py`), Swift tests under `apps/macos/Tests/*`, Python via `.venv/bin/python -I -B -m pytest` with `PYTHONDONTWRITEBYTECODE=1`, full gate `scripts/verify` (about 13 min; only with no training job on the GPU).
