# Plan: prompt catalog in a database — the corpus store

**Goal:** Prompts and catalogs live in an authoritative SQLite database inside the library and are edited at runtime with `voice-lab catalog …` (add, edit, retire, import Harvard/ARCTIC, publish a version, activate). The app loads its catalog from the service at launch instead of from a catalog frozen into the build, so a prompt change is an edit plus a relaunch, never a rebuild. New takes reference the catalog by id, version and hash instead of embedding all of it; every existing take stays readable untouched.
**Out of scope:** Moving take metadata (heads, seals, edits, the journal) into the database — that is a separate, much riskier plan and should wait until this one has proven out. An in-app prompt editor (the CLI is the editor for now; the app only loads). The corpus-first pipeline and Speak page plans (they stay as written; this plan removes their catalog-rebuild step). Retiring the legacy Qt desktop and console. The 1,000-take acceptance track and physical-test roots (untouched).

## Context

- Why a rebuild is needed today: the catalog is a pinned JSON resource (`prompt_catalogs.py`, `BUILTIN_PROMPT_SUITE_SHA256`), frozen into `NativeRecordingApplicationSettings.catalog` (`native_recording_application.py:50`), verified at build with `--expect-catalog-sha256`, and the Swift app builds its prompt list from `configuration.catalog` (`RecordingUI/RecordingWorkspaceModel.swift:155-156`, `RecordingCore/RecordingApplicationConfiguration.swift:10`).
- Why the catalog must stop being embedded: `RecordingGroup.catalog: PromptSuite` (`recording_contracts.py:157`) is inside every `CaptureReservation`, so every take's `head.json`/`reservation.json` carries the whole catalog (measured 2026-09-15: 9,944 of 12,932 bytes with 36 prompts; a 1,886-prompt catalog would be about 500 KB per file, three files per take, and inside every context/reservation event under the 1 MiB control-frame cap). `OpenContextCommand.catalog` (`:619`) embeds it too. Sites that read the embedded catalog: `recording_discovery.py:309,513`, `recording_service.py:613-614,1383`, `recording_index.py:1005,1638`, `recording_packages.py:256,265,298,456`, plus 24 `.catalog.prompts`/`.catalog.purpose` uses.
- What stays authoritative on disk: takes bind the exact prompt they were recorded against (`reservation.prompt`) and the `catalog_sha256`; coverage and the fine-tune corpus key on the prompt's canonical hash. Nothing here changes those rules.
- Existing SQLite: the projection cache `provenance/recording-library/recording-library.sqlite3` (`recording_index.py:57,383`), disposable by design, with migrations applied by `PRAGMA user_version` from `migrations/*.sql` (`recording_index.py:287-320,435-443`; packaged copies are looked up under `resources/recording_migrations` before the source tree). The authoritative store is a different database with different rules (never quarantined, backed by immutable snapshot files).
- Migration conventions (agent-first-coding-style): timestamped `migrations/*.sql` with a header comment and a Down step; schema and data migrations in separate files; a manifest `migrations/active/<name>.md`; `migration:` commit prefix; `_migration` companion files only for temporary dual behaviour. Here the app and service always ship together (frozen build), so no dual-command window exists; the one permanent compatibility rule is that historical takes embedding a catalog are immutable evidence and are read by a versioned contract forever, like the sidecar-less rule in `docs/PROMPT_CATALOG_V2.md` §3.8.
- Cole's decisions to fold in: room tones leave the catalog; the standard Harvard (720) and CMU ARCTIC (1,132) sentence sets are to be added; Fine-tune is explicit. Python only via `.venv/bin/python -I -B` with `PYTHONDONTWRITEBYTECODE=1`; never reset/stash; the app (PID 35990) keeps running until the new build is verified; ask before presence steps.

## Design (what the steps build)

Database `provenance/corpus/corpus.sqlite3` (WAL, mode 0600, opened by the service and the CLI with a file lock; never rebuilt from anything else). Tables, all with column comments in the migration:

- `corpus_prompts` — `prompt_id` (PK), `prompt_created_at`, `prompt_retired_at` (NULL while live), `prompt_source` CHECK in `pilot-v1|pilot-v2|harvard|arctic|manual|import`, `prompt_source_reference`, `prompt_current_revision`.
- `corpus_prompt_revisions` — `prompt_id`, `prompt_revision` (PK pair), `prompt_sha256` (canonical hash of the `Prompt` contract, the same hash coverage uses), `prompt_text`, `prompt_category` CHECK in the nine categories, `prompt_style`, `prompt_instructions`, `prompt_labels_json`, `prompt_expected_seconds` CHECK (0, 120], `prompt_reference_candidate`, `prompt_holdout`, `prompt_revision_keeps_recordings` (0 or 1), `prompt_revision_created_at`. Append-only: editing inserts a revision. By default a new revision invalidates earlier recordings of the prompt (its hash is new, so coverage shows it missing until re-recorded). A revision made with `--keep-recordings` (typo fixes, punctuation, casing) sets `prompt_revision_keeps_recordings = 1`: takes recorded against every earlier revision in the unbroken keep-chain still count, and the corrected text becomes their transcript for training.
- `corpus_prompt_aliases` — `prompt_id`, `prompt_revision`, `accepted_prompt_sha256` (PK triple): the earlier hashes a keep-recordings revision accepts, materialized at publish time so readers never walk the chain themselves.
- `corpus_catalogs` — `catalog_id` (PK), `catalog_suite_id` (the `PromptSuite.suite_id` it materializes to), `catalog_purpose` CHECK, `catalog_created_at`, `catalog_retired_at`, `catalog_description`.
- `corpus_catalog_versions` — `catalog_id`, `catalog_version` (PK pair), `catalog_sha256` UNIQUE (hash of the materialized `PromptSuite`, so every existing `catalog_sha256` field keeps its meaning), `catalog_snapshot_path` (`provenance/corpus/snapshots/<catalog_sha256>.json`, written once, immutable), `catalog_version_created_at`. The snapshot is a `CatalogSnapshot` contract: the exact `PromptSuite`, its `catalog_sha256` (which must equal the file name and the hash of the embedded suite) and `prompt_aliases`, a map from each current `prompt_sha256` to the earlier hashes it accepts. The `PromptSuite` contract itself is unchanged, so prompt and catalog hashes stay comparable with every built-in and every existing take.
- `corpus_catalog_version_prompts` — `catalog_id`, `catalog_version`, `prompt_id`, `prompt_revision`, `catalog_prompt_ordinal`; PK on the first three.
- `corpus_subjects` — `subject_id` (PK), `subject_active_catalog_id`, `subject_active_catalog_version`.

Contracts: `CatalogReference` (catalog_id, catalog_version, catalog_sha256, snapshot_path). `RecordingGroup` schema v2 carries `catalog_reference` instead of `catalog`; v1 (embedded) remains valid input forever. `resolve_group_catalog(layout, group) -> CatalogSnapshot` is the one reader: an embedded catalog becomes a snapshot with empty aliases; a reference loads the snapshot file, verified against `catalog_sha256`; a reference whose snapshot is missing or altered is a hard `SecurityError`, never a fallback. Built-in JSON catalogs become seeds and pins for historical hashes only.

Coverage with aliases: a prompt is covered when a retained take exists whose recorded prompt hash is the prompt's current hash **or one of its accepted aliases**. The index materializes the alias map when it registers a catalog version, and `next_missing`, `_prompt_summary`, history counts and the coverage report all match through it. The fine-tune corpus picks the latest retained take across the same set and records both `recorded_prompt_sha256` (what the audio was recorded against) and the current prompt; the training transcript is the current text.

## Decisions (confirmed by Cole 2026-09-15)

1. Take metadata stays as files; the database holds prompts and catalogs only. A later plan can revisit.
2. ~~Editing a prompt's text makes it a new revision; takes recorded against the old text stop counting for it until re-recorded.~~ Edits invalidate earlier recordings by default, but an edit may be made with `--keep-recordings` (typos, punctuation, casing) so earlier recordings keep counting and the corrected text becomes their transcript. Implemented through prompt aliases in the snapshot; see the Design section.
3. Location `provenance/corpus/` for the database and snapshots, backed up together with the library.
